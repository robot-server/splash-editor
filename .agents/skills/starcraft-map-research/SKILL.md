# 스타크래프트 맵 지식 조사

이 스킬은 기능 구현 사례를 조사하고 `docs/`를 갱신한다. 맵을 만들고 수정하는 [starcraft-map](../starcraft-map/SKILL.md) 스킬과 별개다.

조사에 사용하는 설치 에셋 경로는 `SC_INSTALL` 또는 사용자가 제공한 경로에서만 가져온다. 값이 없으면 필요한 시점에 사용자에게 묻고, 기기 경로를 추측하지 않는다. CLI는 `SPLASH_CLI`가 설정되어 있으면 그 실행 파일을 쓰고, 그렇지 않으면 저장소 빌드본 `./build-cli/src/cli/splash-cli`를 확인한다. 없으면 CLI를 사용할 수 있는 상태인지 먼저 확인하며 옛 생성 스크립트를 열람 도구로 대체하지 않는다.

## 자료와 최신성

- 먼저 기존 `_local-corpus/`를 확인한다. 글 목차·저장 본문·scmscx 맵 ID를 찾아 이미 있는 자료를 재사용한다. 네트워크가 된다는 이유만으로 다시 내려받지 않는다.
- 자료 선정·원문 확인·근거 작성은 [코퍼스 근거 지침](../../../docs/method/corpus.md)을 따른다. 집계값을 근거로 삼지 않는다.
- 스타 에디터 아카데미(스에아)는 기본적으로 [book5095361](https://cafe.naver.com/edac/book5095361)의 글을 사용한다. 로컬 목차와 저장 본문에서 필요한 주제를 찾는다. 그 책에서 필요한 기능을 찾지 못했거나 특정 보충 글을 가리킬 때만 다른 EDAC 책을 조사한다.
- scmscx는 확인할 구체적인 기능이나 공간 구성을 먼저 정해 후보 맵을 찾는다. 검색 결과는 후보 탐색용이다. 제목·인기·개수·분포로 기능을 추정하지 말고, 개별 맵을 열어 구조를 확인한다.
- 코퍼스에 없는 필요한 자료만 새로 받는다. 사용자가 최신화·갱신·재다운로드를 명시한 경우에만 기존 자료도 다시 받는다.
- 공개 scmscx 및 로그인 없이 접근 가능한 네이버 자료는 `tools/research/download_sources.py`를 쓴다. 새 원본 파일은 `_local-corpus/`에만 저장한다. 원본 맵과 글 덤프를 `docs/`에 복사하거나 커밋하지 않는다.

## 네이버 로그인과 강좌 본문 읽기

일부 스에아 글은 로그인된 네이버 세션이 필요하다. 일반 HTTP 가져오기로 읽을 수 없는 글이 필요하면:

1. 브라우저를 조작하기 전에 이 환경에서 제공하는 Browser 스킬을 읽고 따른다. 이미 로그인된 브라우저 세션이 있으면 재사용한다.
2. 로그인 세션이 없으면 설치된 브라우저 지침에서 허용하는 브라우저 표면을 사용한다. 별도 Playwright가 허용되고 준비되어 있는 환경에서는 설치된 Chrome의 영구 브라우저 컨텍스트를 사용할 수 있다. 브라우저 창을 사용자에게 보여 주고 사용자가 직접 로그인하게 한다. 비밀번호·쿠키·인증 저장소를 요청, 입력, 저장, 열람, 내보내기하지 않는다.
3. 로그인 후 같은 브라우저 컨텍스트로 책 목차와 글 링크를 따라간다. 카페 글은 `cafe_main` 또는 중첩 프레임에 렌더될 수 있으므로 바깥 페이지에서 본문을 찾았다고 가정하지 말고 실제 프레임의 표시 내용을 읽는다.
4. 글 URL·제목·읽을 수 있는 본문만 해당 `_local-corpus/edac/` 영역에 저장하고 목차를 갱신한다. 로그인/접근 실패는 미해결로 기록한다. 접근 제한을 우회하거나 다른 자료를 같은 원문인 것처럼 대신하지 않는다.

이전 Claude 작업은 Playwright의 `chromium.launchPersistentContext`와 설치된 Chrome을 사용했다. 눈에 보이는 로그인 단계를 거친 뒤 같은 프로필로 다시 열어 목차·글 링크를 따라가고, 프레임에서 본문을 읽었다. 당시 임시 프로필 경로는 재사용 경로가 아니며 코드·문서에 고정하지 않는다. 브라우저 프로필은 저장소 바깥에 둔다.

## 원본 맵은 CLI의 열람 기능을 모두 활용한다

기능을 기록하기 전에 `splash-cli`에서 확인 가능한 내용을 조사한다. `info`나 트리거 개수만 보고 결론 내리지 않는다. [CLI 열람 목록](references/cli-inspection.md)을 읽고, 현재 빌드의 전체 도움말과 관련 그룹별 도움말을 확인한다. 맵에 적용되는 읽기 전용 뷰를 빠짐없이 열고, 해당 없음·설치 에셋 부재·출력 제한 등 미확인 범위를 적는다. CLI 명령은 바뀔 수 있으므로 실제 바이너리 도움말을 기준으로 한다.

선택한 맵 하나 안에서 관련 근거를 서로 연결한다:

- 맵 크기·타일셋·플레이어 슬롯·세력·스타팅·오브젝트 위치와 렌더 지형;
- 필요에 따른 지형 레이어·이동/건설 속성·두들·스프라이트·시야 가림·로케이션;
- 필요에 따른 유닛 종류·소유자·설정·업그레이드·기술·프리셋·자원·사운드;
- 기능과 관련된 모든 트리거의 소유자·활성 여부·조건·액션 순서·참조 문자열/로케이션/스위치/Deaths·상태 전이;
- 기능이 요구하는 경우 미션 브리핑 순서와 게임 중 다시 볼 수 있는 안내.

트리거는 `trigger show`, `trigger list`, `trigger args`를 각각 전체 텍스트·체인·인자 세부 확인에 사용한다. 렌더와 지형 구역을 대조해 트리거 위치와 오브젝트가 공간상 어떻게 대응하는지 본다. 설치 에셋으로 지형·유닛 속성을 확인한다. 정적 조사만으로 게임 중 성공을 단정하지 않는다. 게임을 열 수 없으면 문서에 한계를 남긴다.

## 기능 메커니즘만 기록

평균·중앙값·빈도표·단순 개수 요약이나 일반적인 스타크래프트 설명을 기록하지 않는다. **무엇을 만들고, 그 문맥에서 왜 작동하며, 각 요소를 어떻게 배치·연결하는지**를 설명한다.

관련 `docs/` 문서를 갱신하거나, 주제가 독립적이면 초점이 분명한 문서를 만들고 해당 README에서 연결한다. 각각의 지식 항목은 아래 세 구획만, 이 순서로 쓴다. 필드 이름도 그대로 사용한다:

```markdown
## [지형/배치 메커니즘]
- 메커니즘 이름:
- 적용 이유/목적:
- 구체적 규칙 (타일 단위, 좌표 단위, 배치 각도, 언덕 연결 규칙 등):
- 잘된 예시 및 실패하는 나쁜 예시:

## [트리거/로직 패턴]
- 패턴 이름:
- 구현하고자 하는 기능:
- 조건(Condition) 및 액션(Action) 구조 체인:
- 예외 처리/버그 방지 로직 (예: 스위치 리셋, 트리거 순서 등):

## [에디터 타일/배치 제약사항]
- 지형 간 연결 규칙:
- 유닛 길막/동선 보장 규칙:
```

트리거 구획은 유즈맵 데이터에 적용한다. 밀리 원본에서 트리거 관찰이 실제 기능 설계에 중요할 때는 관찰 범위를 분명히 적는다.

각 필드는 위 예시와 같은 이름을 사용한다. 해당하지 않는 구획도 빼지 말고 “해당 없음”과 짧은 이유를 쓴다. 출처 링크, 관찰 범위, 미검증 상태 및 런타임 한계는 이 세 구획 안의 관련 필드에 포함하며 별도 상위 구획을 더하지 않는다. 출처 링크는 scmscx 맵 ID 또는 스에아 글 URL로 붙인다. 저장소 문서에 사용자의 맵 파일명을 쓰지 않는다. 원본이 실제로 보여 주는 내용과 추가 안전 권고를 구분한다. 기존 문서를 편집할 때도 통계를 새로 추가하지 않으며, 기능 설명을 일반 게임 상식으로 늘리지 않는다.

## 문서 변경 후 적대적 검토

문서 수정을 마친 다음 적대적 서브에이전트에게 변경 문서를 검토시킨다. 사실 주장, 트리거 순서와 상태 전이, 기하·좌표 규칙, 출처 추적성, CLI/정적 검사가 증명하는 범위를 과장했는지 따져 달라고 한다. 검토자에게 근거 자료와 변경 문서는 주되, 의심 항목이나 예상 결론은 알려 주지 않는다. 보고된 문제마다 실제 원본 맵/글, CLI 출력, 코드 또는 게임 동작과 대조한다. 확인된 결함만 고친 뒤 영향받은 주장을 재검토하고 상대 링크와 `git diff --check`를 확인한다.

서브에이전트에게 원본 확인을 대신시키거나 통계 요약을 근거로 받아들이게 하지 않는다.
