# StarCraft 맵 제작 공통 절차

`starcraft-map-melee`와 `starcraft-map-usemap` 스킬이 공유하는 절차·도구·판정 규칙이다. 두 스킬 모두 이 문서를 먼저 따르고, 각 SKILL.md는 여기 없는 내용만 추가한다.

## 도구와 경로

`splash-cli`와 Python 생성기·조립 도구를 맵 제작 도구로 쓴다 — 장르별 생성기는 각 스킬 자신의 `scripts/`(`.agents/skills/starcraft-map-melee/scripts/`·`.agents/skills/starcraft-map-usemap/scripts/`)에, 둘이 공유하는 핵심 도구(`scmap`, `spatial`, `verify_map`, `preview`, 코퍼스 측정 스크립트, 코퍼스 데이터 `data/`)는 `tools/mapgen/`에 있다. 각 스킬의 `scripts/scmap.py`는 `tools/mapgen/scmap.py`를 가리키는 심볼릭 링크다 — 실제 코드는 한 곳에만 있다. 요청한 장르와 가까운 레시피가 있으면 그 코드와 옵션을 살펴 출발점으로 삼고, 맵 목적·타일셋·인원에 맞춰 조정한다. 생성기 출력은 완성 증거가 아니므로 맵 구조·렌더·게임 동작을 따로 확인한다. 램프 등 개별 분석 도구는 해당 문서에서 측정 범위와 한계를 확인한 뒤 쓴다. 새 맵은 레포가 아닌 사용자의 StarCraft `Maps` 폴더 아래에 둔다. 개인 경로를 코드·문서·예시에 하드코딩하지 않는다. `STARCRAFT_MAPS`가 있으면 우선 쓰고, 없으면 기기에서 설치/사용자 Maps 폴더를 찾아 선택한다. 후보가 모호하거나 찾지 못하면 사용자에게 경로를 묻는다. 임의 fallback으로 레포에 저장하지 않는다.

`tools/mapgen/data/`의 코퍼스 집계 JSON과 이전 결과물은 설계 목표나 정답의 근거가 아니다. Python 생성기와 조립 도구는 재사용 가능한 구현 레시피로 검토하되, 그 안의 통계 기본값·추론·검사 범위가 요청한 맵에 맞는지 확인한다. 지형·기능·배치 선택은 [docs/README.md](README.md)에서 관련 메커니즘 문서로 이동해 근거와 적용 범위를 확인하고, 문서의 관찰과 권고를 구분해 적용한다.

설치 에셋이 필요한 작업은 사용자가 제공한 설치 경로 또는 `SC_INSTALL`을 쓴다. 경로를 임의로 가정하지 않는다.

## 진행 순서

맵마다 Plan → Implement → Test → Review/Fix-Refine 순서로 진행한다. 앞 단계를 건너뛰고 생성기부터 돌리지 않는다. 생성기를 돌리기 전에 이 맵을 구체적으로 어떻게 만들지 먼저 설계한다(Plan). 레시피·근거 문서 확인은 이 설계를 뒷받침하는 자료일 뿐 설계 자체가 아니다. Plan에서 정한 값은 Implement 단계에서 그대로 옮기고, 여기서부터는 Plan을 뒤집지 않는다 — 생성 중 Plan과 안 맞는 제약을 발견하면 Implement를 계속하지 말고 Plan으로 돌아가 다시 정한다. 각 장르에서 Plan 단계에 정할 값과 Implement 단계의 인자화 방식은 해당 SKILL.md를 따른다.

문서의 수치 빈도, 평균, 중앙값을 설계 목표로 복사하지 않는다.

`docs/`에 정리된 원본 관찰은 해당 문서의 출처와 적용 범위를 따른다. 문서에서 다루지 않은 동작이나 서로 충돌하는 사례가 있을 때만 원본을 추가 조사하고, 확인하지 않은 세부사항은 사실처럼 채우지 않는다. 관찰된 패턴과 추가로 권장하는 예외 처리/검증 규칙을 구분한다.

## 제작 전에 확인하는 공통 제약

아래 문서의 제약만 확인하고, 그 본문이나 유닛 목록을 맵 설명에 복사하지 않는다. 장르별 추가 제약은 각 SKILL.md에 있다.

- [튕김 배치](./game/crashes.md)는 Null 타일·맵 밖 유닛·건물 최대 체력 0을 남기지 않는다.
- [시간 단위](./game/time.md)는 Wait와 Countdown을 초 단위 타이머로 두지 않는다.
- [런타임 판정](./game/rules.md)은 고저 시야, 이동 연결, 공격 사거리를 같은 판정으로 보지 않는다.
- [미사용 유닛·보호 해제](./limits.md)는 미사용 유닛 번호와 남의 맵 보호 해제를 사용자 허락 없이 하지 않는다.
- [EUD](./eud/limits.md)는 허락과 대상 판본 확인 없이 넣지 않고, 게임 밖 메모리·상대 클라이언트 파괴·숨은 동작을 만들지 않는다.
- [AI 스크립트](./trigger/ai-scripts.md)는 컴퓨터 슬롯·종족·필요 유닛·로케이션이 스크립트와 맞을 때만 쓴다.
- [유닛 설정](./unit/settings.md)은 Use Defaults를 끄기 전에 적용되지 않으며, 유즈맵 설정을 밀리 모드 결과로 판정하지 않는다.
- [피해](./unit/damage.md)는 표시 피해를 방어력과 공격 형태 배율 뒤의 값으로 보고, 폭발형을 스플래시와 같은 것으로 두지 않는다.
- [영웅](./unit/heroes.md)은 이름만으로 일반 유닛보다 강하다고 두지 않으며, 골리앗·시즈는 포탑, 캐리어는 인터셉터 무기를 본다.
- [트리거 텍스트](./trigger/api.md)는 classic 편집기 창의 필드 순서를 CLI 인자 순서로 복사하지 않는다.

## Test (확인 및 저장)

맵 변경 후 렌더를 확인하고 `verify_map.py <맵>`을 돌린다. `--json`은 종료 코드가 항상 0이라 이 관문으로 쓰지 않는다. 맵을 버리는 조건은 그 종료 코드가 0이 아닌 것뿐이다. 종료 코드 0은 플레이가 된다는 뜻이 아니므로 아래 게임 동작 확인을 따로 한다. 실패는 맵 밖 유닛, 못 걷는 땅 66% 초과, 불 효과가 있는 건물의 체력 0, 사용 안 함·닫힘 슬롯만의 진행 트리거, 깨진 자원 비트, 스타팅이 없거나 걸을 수 없음, 확장자·버전 불일치, 죽음 수를 변수로 쓰는 유닛이 배치됨, Modify Unit 인자 순서처럼 어느 컨셉에서도 잘못된 항목이다. `?`로 찍히는 대칭, 거리, 자원량, 종족 기울기, 검은 칸, 타일 다양성, 비콘 주변, 브리핑·소리·포스·스위치의 유무, 타이머 숫자, UNIS 전 필드 0은 보고일 뿐이라 그 이유만으로 맵을 버리지 않는다. OpenBW·bwheadless·게임 실행은 이 관문이 아니다.

프로필에 적은 시간이 화면에 보일 숫자면 Countdown Timer·Elapsed Time에 그 숫자를 그대로 넣는다. 실제 초를 맞추는 값이면 저장본 숫자가 `scmap.game_ticks` 결과와 같아야 한다. 다르면 그 맵을 쓰지 않는다. 어느 쪽인지는 맵 파일만으로 알 수 없으므로 이 비교는 프로필을 보고 한다.

트리거 발동·건물 자리·일꾼 채집·램프 통과는 정적 검사로 확정하지 않는다. 가능한 경우 게임에서 열어 확인하고, 실행 확인을 할 수 없으면 제한을 명시한다.

생성기 완료 뒤 자원 누락·의도한 멀티/방 연결 누락·최종 스타팅 연결 실패가 있으면 그 결과를 사용하지 않는다.

맵은 사용자의 `Maps` 하위 폴더에 명시된 출력 경로로 저장한다.

## Review / Fix-Refine (주장 범위와 반증)

Test를 통과했다고 완성으로 보지 않는다. 최종 맵에서 프로필이 의도한 지형·유닛·UNIS·업그레이드·기술·트리거 동작이 Plan대로 나왔는지 다시 확인한다. 어긋난 부분이 있으면 Fix로 그 부분만 다시 Implement하고, Plan 자체가 틀렸으면 Plan부터 다시 한다.

`docs/`나 [BACKLOG.md](../BACKLOG.md)에 "항상", "전부", "무엇을 바꿔도" 같은 일반화 문장을 적을 때는 시험한 조합(타일셋·크기·인원·inset·시드 등)의 표와, 반례를 찾아본 적이 있는지를 함께 적는다. 표가 없으면 "이 조합에서 재현됨"으로만 적고 범위를 넓히지 않는다. 실제로 이전에 "radial 대칭이 인원·타일셋·크기·inset 무엇을 바꿔도 항상 실패한다"고 적혔던 기록이, 성공 사례(6인 Jungle Cross, 8인 Jungle Radial)가 나오면서 "badlands+128 좁은 조합에서만 실패"로 정정된 적이 있다.

아래 세 경우에는 결론을 그대로 적거나 전제로 쓰기 전에, 같은 컨텍스트를 공유하지 않는 별도 서브에이전트에게 근거 위치·적용 조건·재현 절차를 요구하며 반증을 맡긴다.

- 오래 남는 일반화 주장을 문서(BACKLOG.md, docs/)에 새로 기록하려 할 때
- 같은 실패가 서로 다른 시도에서 3번 이상 반복됐을 때
- 검증된 적 없는 조합(새 타일셋, 새 대칭, 새 생성 방식 등)을 쓰려 할 때

반증 결과는 재현 명령과 수치가 딸려 있을 때만 채택해 문서를 고친다. 근거가 없으면 기각하고, 기각한 이유(무엇을 재현해봤더니 어땠는지)를 남긴다. 다른 세션이나 이전 fork가 낸 결론도 같은 기준으로 다룬다 — 검증 전에는 사실이 아니라 가설로 취급한다.
