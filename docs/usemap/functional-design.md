# [트리거/로직 패턴]

## 선택 토큰을 보상 유닛으로 교체

- 패턴 이름: 위치 선택 후 토큰 소비와 보상 생성
- 구현하고자 하는 기능: 선택 유닛을 지정 영역으로 이동시켜 영웅·아이템·단계 중 하나를 고른다.
- 조건(Condition) 및 액션(Action) 구조 체인: [원본 선택 맵](https://scmscx.com/map/954qzrkz)에서 `Bring(Current Player, Terran Civilian, 선택 위치, At least, 1)` → `Preserve Trigger` → `Center View(부활 장소)` → `Create Unit(선택 보상, 부활 장소)` → `Kill Unit At Location(Current Player, Terran Civilian, 1, 선택 위치)` → 결과 메시지 순서를 확인했다. 별도 [원본 구매 맵](https://scmscx.com/map/2BqjYVjT)은 `Bring(Current Player, 선택 유닛, 위치 03, At least, 1)` + `Accumulate(Current Player, At least, 비용, ore)` + `Deaths(Player 7, Terran Beacon, At least, 1)` → 토큰 제거 → 영웅 생성 → 자원 차감 → 성공 메시지·효과음 → `Preserve Trigger`로 연결한다.
- 예외 처리/버그 방지 로직 (예: 스위치 리셋, 트리거 순서 등): 위치 토큰을 제거하는 것은 이 체인의 재구매/재선택을 막지만, 원본 성공 경로에는 보상 생성 공간 또는 생성 실패를 판정해 환불하는 분기가 보이지 않는다. 새 맵에서는 토큰·자원을 소비하기 전에 생성 위치가 비었는지와 한 번에 만들 수량을 게임에서 확인하고, 실패했을 때 상태를 되돌릴지 설계한다. 선택 상태로 쓰는 Switch는 다음 라운드에서 다시 쓸 경우 명시적으로 초기화한다. 동일 플레이어의 트리거는 위에서 아래로 처리되므로 생성·제거 순서를 의도대로 둔다. [강좌: 트리거 작동 원리](https://cafe.naver.com/edac/book5095361/76436)

## 비콘/상점에서 자원 확인 후 구매

- 패턴 이름: 위치 조건과 자원 조건으로 구매를 승인
- 구현하고자 하는 기능: 플레이어가 상호작용 위치에 들어왔을 때 특정 비용을 내고 유닛 또는 효과를 얻는다.
- 조건(Condition) 및 액션(Action) 구조 체인: 위 [원본 구매 맵](https://scmscx.com/map/2BqjYVjT)에서는 선택 유닛을 구매 위치 `03`으로 가져온다. 비용과 Player 7의 Beacon 사망 수를 함께 검사한 뒤 선택 유닛 하나를 제거하고 영웅을 만들며, 성공 메시지와 소리를 출력하고 반복 허용한다. 구매 비용·선택 번호·보상 위치는 유닛 종류에 따라 달라지므로 조건과 액션을 한 세트로 대조한다.
- 예외 처리/버그 방지 로직 (예: 스위치 리셋, 트리거 순서 등): 조사한 성공 체인만으로 잔액 부족 안내, 생성 실패 환불, 동시 구매 원자성이 확인되지는 않는다. 해당 분기는 별도 제작 항목으로 설계하고 실제 게임에서 자원·생성 결과를 확인한다. 가격·효과는 상호작용 전에 읽을 수 있게 지속형 미션 목표/안내판 등 맵이 실제 제공하는 인터페이스에 적고, 트리거의 가격·보상과 대조한다. `Display Text Message`의 `Always Display`는 게임 자막 옵션이 꺼져 있어도 해당 문구가 출력되게 하는 설정이지 HUD에 영구 표시하는 기능이 아니다. [강좌: 트리거 액션](https://cafe.naver.com/edac/book5095361/76412)

## 단계 진행과 반복 실행을 분리

- 패턴 이름: Switch/Death Count로 진행 상태 표현
- 구현하고자 하는 기능: 안내, 선택, 웨이브, 보상 등에서 현재 단계에 맞는 상호작용만 실행한다.
- 조건(Condition) 및 액션(Action) 구조 체인: scmscx 원본은 `Bring` 및 자원 조건에 `Deaths` 또는 `Switch`를 결합해 선택 종류·현재 상태를 구분하고, 처리 액션 끝에 `Preserve Trigger`를 둬 반복 검사했다. 스에아 강좌의 예시는 적 웨이브 상태를 Switch로 가르고 완료 뒤 상태 전환과 보상을 연결한다. [강좌: 트리거 중요 기능](https://cafe.naver.com/edac/book5095361/76451)
- 예외 처리/버그 방지 로직 (예: 스위치 리셋, 트리거 순서 등): 상태를 바꾸는 액션이 조건과 같은 주기에 다시 참이 되는지 확인한다. `Wait`가 있는 같은 플레이어의 트리거는 서로의 실행을 지연시킬 수 있으므로, 독립 타이머를 운용할 때는 트리거 소유자와 실행 순서를 고려한다. 한 Force에 `Bring`을 걸고 플레이어별 실행 블록을 반복하면 플레이어별로 같은 효과가 중복되는지 점검한다. 강좌는 동일 플레이어 트리거의 위→아래 순서와 `Wait`의 직렬 영향을 설명한다.

## 시작 브리핑과 게임 중 지속 안내 분리

- 패턴 이름: 시작 전 학습과 플레이 중 재참조를 별도 제공
- 구현하고자 하는 기능: 짧은 맵 설명으로 플레이 유형을 알리고, 브리핑에서 임무·조작·상태·상호작용 결과를 설명한다. 게임 중에도 가격이나 비콘 효과를 다시 확인할 수 있게 한다.
- 조건(Condition) 및 액션(Action) 구조 체인: 맵 설명에는 선택에 필요한 요약만 둔다. Mission Briefing은 조건 분기 없는 순차 액션으로 작성한다. `Mission Objectives`에는 목표와 규칙을 두고 `Text Message`에는 필요한 조작과 진행 설명을 둔다. 게임 중 반복 안내가 필요하면 해당 위치/상호작용 상태를 조건으로 별도 트리거 메시지를 제공한다. [강좌: 미션 브리핑과 스트링](https://cafe.naver.com/edac/book5095361/76453)
- 예외 처리/버그 방지 로직 (예: 스위치 리셋, 트리거 순서 등): Briefing 액션은 조건 분기가 없으므로 게임 중 상태에 따라 달라질 문구를 넣지 않는다. `Always Display`는 자막 설정에 따른 표시 누락을 막지만 영구 표시가 아니다. 계속 참조할 정보는 `Mission Objectives`처럼 플레이 중 다시 열 수 있는 인터페이스에도 두고, 진입 반복 메시지는 스위치/데스값이나 재진입 조건으로 빈도를 통제한다.

# [지형/배치 메커니즘]

## 트리거 상호작용에 읽히는 공간을 함께 배치

- 메커니즘 이름: 상호작용 표식·대상·안전 이동 공간의 시각적 짝짓기
- 적용 이유/목적: 플레이어가 비콘/영역의 기능과 도착 후 보상을 공간만 보고도 예측하고, 생성 유닛이 막히지 않게 한다.
- 구체적 규칙 (타일 단위, 좌표 단위, 배치 각도, 언덕 연결 규칙 등): 스에아의 [로케이션에 가면 유닛을 생산하기](https://cafe.naver.com/edac/book1678930/19898)는 비콘과 결과 유닛을 먼저 보이게 배치하고 나서 로케이션을 지정하는 예를 든다. 상호작용 공간, 결과 유닛이 놓일 자리, 이동 목적지를 각각 식별하고 건물·유닛과 겹치지 않게 둔다. 생성 수량을 담을 공간을 예약하되, 공간이 충분한지와 게임의 생성 실패 반응은 직접 테스트한다.
- 잘된 예시 및 실패하는 나쁜 예시: 비콘 옆에 결과 유닛이나 설명이 보여 기능을 예측할 수 있고, 도착 유닛이 이동할 연결 통로가 있으면 성공이다. 상호작용 유닛이 보이지 않는 곳에 생성되거나, 좁은 지점에 겹쳐 생성되어 길을 막으면 실패다.

## 유닛 종류별 생성 제약 분리

- 메커니즘 이름: 생성 유닛의 건설 크기·점유 처리 확인
- 적용 이유/목적: 한 종류의 유닛이 겹쳐 생성된 사례를 일반 유닛에도 통한다고 오해하지 않고, 반복 생성 뒤 `Can't`가 나는 조건을 실제 재현으로 좁힌다.
- 구체적 규칙 (타일 단위, 좌표 단위, 배치 각도, 언덕 연결 규칙 등): 스에아 [유닛 속성별 생성·충돌 예외](https://cafe.naver.com/edac/book5095361/88226)는 Powerup·Beacon 유형이 다른 유닛/건물과 겹쳐도 강제 생성될 수 있으며, Beacon은 유닛의 건설 크기 조건을 만족해야 한다고 구분한다. 이 예외를 일반 전투 유닛의 `Create Unit` 동작으로 일반화하지 않는다. 생성 예정 수량이 들어갈 위치 footprint, 기존 유닛·건물과의 겹침, 지형의 건설/이동 속성을 유닛별로 대조하고 실제 게임에서 같은 상태를 재현한다.
- 잘된 예시 및 실패하는 나쁜 예시: Beacon/Powerup의 예외와 일반 병력 스폰을 별도 검증하고, 일반 병력은 목적지까지 이동할 공간도 확보하면 성공이다. Beacon 예외를 근거로 군단 유닛을 점유 구역에 대량 생성하거나, 지도에서 빈 공간이 보인다는 이유로 동시 유닛 한도까지 무시하면 실패다.

# [에디터 타일/배치 제약사항]

## 지형 연결과 트리거 생성 공간

- 지형 간 연결 규칙: 지상 생성 위치에서 목표 위치까지 걷기 가능한 영역이 이어져야 한다. Pathfinder Regions 오버레이는 길찾기 연결 문제를 찾는 참고이며, 실제 유닛 경로를 보증하지 않는다.
- 유닛 길막/동선 보장 규칙: 트리거가 반복 생성하는 위치는 대상 유닛 종류별 footprint와 주변 유닛·건물·장애물, 동시 생성량, 이후 이동 경로를 확인한다. Beacon/Powerup의 강제 생성 설명은 일반 유닛과 구분한다. 생성 성공 판정이 없는 트리거 체인은 실제 게임에서 재현해 보고, `Can't`가 뜬 조건을 유닛 종류·점유·지형·활성 유닛 상태별로 좁힌다. 확인하지 않은 원인을 보편 규칙으로 적지 않는다.

## 비콘 이름과 효과의 공간 표식

- 효과 예측 규칙: 비콘을 밟기 전에 무엇이 일어날지 알 수 있어야 한다. 비콘
  주변 약 4타일 안에 효과를 나타내는 유닛/건물/상징을 짝으로 놓는다. 해당
  타입의 맵 표시 이름에 결과와 핵심 비용을 적는다. CLI는
  `unitdef set <맵> <유닛> --name <이름>`을 지원한다. 예: `Siege Tank · 150 ore`,
  `Medic · heal`, `Cloak · 80/60`. 정확한 가격이 트리거와 표식에서 일치하는지
  확인한다.
- 범위: 코퍼스에서 Beacon류 3,771개를 셌을 때 93.3%가 다른 오브젝트와
  4타일 이내, 98.8%가 8타일 이내였다. 이는 공간 근접도 실측이며, 주변 물체가
  항상 결과 설명용이란 증거는 아니다. 읽히는 짝을 의도적으로 만든다.
- 타입 이름 범위: UNIS/UNIx 커스텀 이름은 개별 배치 인스턴스가 아니라 유닛
  타입 전체 설정이다. 한 타입을 여러 효과에 재사용하면 이름도 서로 모순되므로,
  효과마다 고유 타입을 쓰거나 동일한 의미에만 타입을 할당한다. 시작 시 한 번
  나오는 Display Message만 효과 안내로 쓰지 말고, 비콘 옆 이름과 표식에서
  다시 확인할 수 있게 한다.

## 구매 전 선택 유닛·자원·상태 토큰 검사

- 패턴 이름: 선택 유닛을 비용 지불과 보상 유닛으로 교환
- 구현하고자 하는 기능: 플레이어가 결과가 보이는 비콘/상점 위치로 선택 유닛을
  가져가고, 충분한 자원과 유효한 상태일 때만 그 유닛을 보상과 교환한다.
- 조건 및 액션 구조: 코퍼스의 읽힌 채용 체인에서는 `Bring(Current Player,
  선택 유닛, 상점, At least, 1)` + `Accumulate(Current Player, At least, 비용,
  ore)` + `Deaths(Player 7, Terran Beacon, At least, 선택 번호)` 뒤 선택 유닛을
  지우고 영웅을 만들며, 자원을 차감하고 결과 문구/소리를 낸 다음
  `Preserve Trigger`로 반복 판정한다. `genre-recipes.md`에는 단일 성공 체인
  필터로 계산한 코퍼스 범위와 대표 예를 구분해 둔다.
- 코퍼스 검색: 읽을 수 있던 369개 맵 중 15개에서 Custom 액션 없는 단일 트리거에
  선택 유닛 Bring, Accumulate 비용, 상태 Deaths, 선택 유닛 소비, Create Unit,
  ore 차감이 함께 있었다. 이 좁은 서명은 발견용 검색값이며 모든 상점 유형을
  포괄하지 않는다. 대표 성공 체인의 원본 세부는 [장르 레시피 문서](genre-recipes.md)에
  기록했다.
- 실패/반복 규칙: 자원·유닛 제거 뒤 생성하는 순서에서는 생성 칸이 막힌 경우
  결제만 되고 보상이 안 나올 수 있다. 소비 전에 자리 조건을 확인하거나
  실패/환불 분기를 둔다. 동시 구매나 영구 반복이 의도된 것이 아니라면
  선택 토큰 제거 또는 Deaths 상태 변경을 보상 생성과 함께 실행한다.
- 새 레시피 예: [`make_loadout_gauntlet.py`](../../.agents/skills/starcraft-map/scripts/make_loadout_gauntlet.py)는
  코퍼스의 성공 구매 고리를 드래프트 선택으로 한 번만 사용하고, 선택 완료 후
  별도 협동 웨이브 상태로 넘어간다. 원본 관찰과 새 연결 방식은 같은 것으로
  취급하지 않는다.
